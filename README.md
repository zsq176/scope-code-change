# 控制代码变更范围

`scope-code-change` 用于在实现之前界定每次代码变更的范围，并把变更控制在合适的规模内。适用于功能开发、缺陷修复、重构、优化或会改变行为的配置调整，确保变更符合项目的核心目标、需求优先级、复杂度预算和长期可维护性。

在编辑代码之前，先明确：

- 项目主线：项目存在的首要目的，以及它必须交付的核心行为。
- 用户结果：用直白的语言复述必须发生的变化，同时说明用户没有要求什么。
- 需求等级：主线需求、支撑需求、次要需求，还是罕见的长尾事件。
- 根本原因：找出有效状态首次变为无效状态的节点，以及导致该问题的错误假设。
- 最小结果：能够端到端满足请求的最小行为。
- 变更预算：预计涉及的文件、约新增的代码行数，以及引入的新概念。

实现前，应在 commentary 中简要说明以上内容。判断必须基于当前仓库，而不能只看用户请求。

## 优先消除问题源头

在设计如何处理问题之前，先找出反复制造该问题的机制，并判断能否移除它，或从根本上让它无法发生。相比在下游增加保护、重试、修复任务和恢复分支，应优先恢复被破坏的不变量，移除错误输入或错误假设，或者删除不必要的状态与路径。

同一症状反复出现，说明制造问题的机制仍然存在。加强遏制并不等于问题正在被消除。只有在问题源头已经移除，或者有明确证据证明源头来自外部且无法在当前范围内消除之后，才添加遏制或恢复机制。

## 根因门禁

修复缺陷时，在能够具体说明以下各项之前，不要修改程序行为：

1. 原始故障，以及产生该故障的准确路径。
2. 正确输入首次变为错误状态或错误输出的位置。
3. 代码中的错误假设，并有日志、复现过程或观测值作为依据。
4. 能够消除根因的最小状态转换。

对每项拟议变更进行分类：

- **根因修复（Root fix）：** 防止无效状态被创建。
- **损害遏制（Containment）：** 在状态已经无效后限制损害。
- **故障恢复（Recovery）：** 在故障发生后恢复状态。
- **证据补充（Evidence）：** 让因果链中未知的环节变得可观测。

损害遏制、故障恢复和证据补充可能有价值，但不能被包装成根因修复，也不能不断累积并代替根因修复。如果证据不足，只添加确认问题所需的最少可观测性；获得证据之后，再修改程序行为。

每次尝试修复后，都要重新测试用户最初报告的症状。如果症状仍然存在，应先否定或撤销该次尝试，再添加其他修改。连续两次尝试失败后，停止继续打补丁，从原始输入边界重新构建因果链。如果无法用一句话解释修复原理，或者解释中仍需使用“莫名其妙”“可能”“应该”等词，就说明尚未真正理解这次修复。

## 决策规则

1. 保护项目主线。次要功能不应明显扩大系统规模、拖慢系统、模糊核心逻辑或降低主要系统的稳定性。
2. 优先消除问题生成器。应尽量让故障无法发生，而不是长期依靠检测、修复、重试或限制损害。
3. 复用现有路径。除非缺少新层级、子系统、账本、状态机或框架就无法实现最小结果，否则不要引入它们。
4. 优先实现常见路径。处理高概率或高成本的故障；低概率长尾事件应推迟到真实发生时处理，除非用户明确提高了它们的优先级。
5. 有意控制次要功能的规模。功能可用且便于维护就已足够，不要为了完善次要功能而牺牲主程序。
6. 保持请求范围之外的语义不变。不要仅仅为了让局部修改显得更整洁，就重新设计策略、架构或执行行为。
7. 让验证强度与风险匹配。测试发生变化的路径和关键不变量，不要扩展成与请求无关的全面审查。
8. 先修复生产者，再修复消费者。下游检测到错误状态时，首先修正创建该状态的代码；只有在根因修复无法覆盖代价高昂的故障模式时，才增加下游保护。

## 复杂度约束

将拟议变更与整个仓库的规模进行比较。如果一项支撑功能或次要功能接近项目规模的显著比例、引入多个新概念，或者超过初始代码行数预算的大约两倍，应停止编辑并简化设计。

对于局部缺陷，大范围恢复机制、新状态机或数百行代码通常都应视为超出范围。只有在明确证据表明根因确实横跨如此大的代码范围时，才能继续采用这类方案。

优先选择更少的状态、更少的分支、更少的文件，以及一条显而易见的数据流。可维护性是需求的一部分，而不是实现完成后的清理工作。

## 交付前检查

确认：

- 用户要求的行为能够端到端正常工作。
- 主路径仍然清晰易懂，并且保持完整。
- 实际 diff 与事先声明的变更预算接近。
- 没有遗留临时测试、调试文件或脚手架。

# Scope Code Change

以与风险相称的严谨度执行代码变更任务 —— 全系统影响意识、精确到行的计划、基于证据的验证、诚实的汇报。适用于非平凡变更（多文件行为改动、并发/性能类声明、跨子系统影响）；琐碎修改走轻量路径，零仪式。绝不在没有证据的情况下声称完成。

> 本 README 是 [SKILL.md](SKILL.md) 的全文完整中文翻译，内容以英文原文为准。

## 安装

将本仓库克隆（或复制）为 skill 目录：

## 核心哲学

五条理念约束每一次变更，无论大小：

1. **动手前先了解系统。** 任何变更都存在于更大的系统之中；在选择实现之前，先弄清它还会触及什么 —— 包括它**不得**扰动的东西。
2. **证据胜于自信。** "能跑 / 修好了 / 变快了"需要观察来支撑：一个通过的场景、一组实测对比、一个复现的 bug。听起来合理的论证不是证据。
3. **修因，而非修症。** 在求助于重试、防护、冷却或大范围加锁之前，先移除失败的根源。围堵不是修复。
4. **以可验证的原子为单位工作。** 每个变更单元都是可独立验证的最小行为变更，有明确的代码位置和可观察的验收标准。
5. **经济且诚实。** 交付最小完整表达；删除被替换的东西。一个失败的检查只有在校验对象真正改变之后才能转为通过 —— 绝不靠改措辞把结论"洗"成通过；如实报告局限，而不是声称完成。

严谨度与爆炸半径成正比，与习惯无关。选择下面能覆盖任务风险的最轻路径：在小任务上省略仪式是正确的；省略证据永远不对。

## 选择路径

先花一分钟评估爆炸半径，然后选定：

- **轻量路径** —— 小且清晰：单个函数或文件，行为显而易见，易于验证（typo、日志文案、界面文案、配置值、孤立 bug）。
- **标准路径** —— 跨几个文件的行为变更，或任何一眼看不出失败模式的改动。这是默认选项。
- **完整路径** —— 架构或并发变更、性能类声明、跨子系统边界的变更，或用户标记为重大的工作。

在两条路径之间犹豫时：分析取重，仪式取轻。仅索取计划的请求永远不会授权修改生产代码、部署或交易；诊断工作必须在用户授权范围内 —— 证据需要更多权限时，先询问。

## 轻量路径

1. 扫一眼调用方和相关状态，排查隐藏耦合 —— 一次搜索，不是一张矩阵。
2. 做出变更；通过运行受影响的场景或测试来验证。
3. 汇报改了什么、以及它生效的证据。完成。

## 标准路径

四个问题，按顺序。每个问题用几句话回答之后，再进入下一个。当某个答案暴露出问题，先修正该产物再重新回答；当它推翻了更早的答案，回到上游 —— 不要带着残破的计划继续打补丁。若用户只要计划，回答完问题 2 即停止。

1. **影响面** —— 这次改动触及哪些子系统、数据流和行为，包括它不得扰动的东西？
2. **计划** —— 对每个原子目标：成因（标注事实 / 推断 / 未知）、`file:line` + 符号级别的精确目标、变更后的行为、可观察的验收标准。若成因尚未证实，规划一个区分性实验，而不是投机性修复。不接受不可测试的方向 —— "优化"、"加固"要么成为具体目标，要么不属于这里。
3. **验证** —— 证明关键机制：复现 bug、运行区分性测试、测得对比数据。仅靠读代码无法证明运行时或性能层面的论断。小的可逆实验可以（在授权范围内；其产物事后清理）—— 但它不是交付物。
4. **审计与清理** —— diff 与计划一致、验收通过、被替换的代码已删除、没有遗留的脚本或临时文件。

## 完整路径

对高风险或全系统范围的工作，同样四个问题升级为正式发布的阶段。每个阶段以一行门禁报告结束，然后才进入下一阶段：

> **阶段 N：PASS/FAIL** —— 决定性证据 · 下一阶段（或回退到的阶段）

FAIL 只有在校验对象、证据或假设真正改变之后才能清除。若不存在获得所需证据的授权途径，报告阻塞 —— 绝不在未证实的提案上空转，也绝不伪造通过。

**阶段 1 —— 影响矩阵。** 每个子系统一行，*包括实质上不受影响的*：所有者 + 代码证据、是否可能变化、面临风险的不变量、所需的回归检查。在存在之处覆盖：数据接入、领域逻辑、风控/校验、请求/事务生命周期、派生状态与余额、核算、持久化/投影、API/前端、配置/热加载、可观测性、启动/重连/恢复、并发所有权、操作员工作流。以"未来计划必须遵守的系统边界"收尾 —— 不许把偏好的修复方案偷运进来。

**阶段 2 —— 原子计划。** 每个目标：证据与成因（事实/推断/未知）、`file:line` + 符号级目标、正常/失败/重启路径上的行为与状态转换、验收标准（含用户的原始场景）、依赖关系、明确的不变更项。

**阶段 3 —— 经验检查。** 将下方设计原则套用到已产出的计划上。只记录适用的原则，每条注明它检验的计划决策及修正。发现弱点 → 修订并重新发布被修改的目标（未变的目标保持有效，声明即可）。系统影响发生变化 → 回到阶段 1。

**阶段 4 —— 有效性证据。** 对每个关键机制给出非推断性证明：区分性复现、实测 A/B、或在匹配条件下的直接观察。记录基线、变更条件、结果与局限。仅索取计划的任务到此结束，清理完实验产物后收尾。

**阶段 5 —— 实现。** 复核行号目标，然后逐个目标实现，验证一个再开始下一个。发现计划假设错误，回到阶段 1 —— 而不是伪装成小调整的悄悄重构。

**阶段 6 —— 审计。** 将每个目标映射到实际变更的代码行；审查 diff 的缺陷、回归与并发隐患；运行验收，并在交付路径上复现阶段 4 的证据。构建通过不等于验收。

**阶段 7 —— 清理。** 移除实验产物、死分支、重复状态与过度设计；确认结果是已证实计划的最小完整表达。若清理改变了行为，重新审计。然后交付：最终答复汇报通过的路径、证据与诚实的局限 —— 它是对门禁报告的补充，而非替代。

## 设计原则

标准路径问题 2 与完整路径阶段 3 的检查清单。只套用相关的条目；不要为了填矩阵而凑数。领域专属条目放在 `references/` 下的可选扩展包中，按需加载 —— 本仓库附带一个交易 / 链上交易示例（[references/market-trading.md](references/market-trading.md)）；其他领域照此方式衍生自己的扩展包即可。

**产品**

- 先可用，再好用：预期行为、所需并发、延迟、停止/重启/恢复、可理解的结果。"没报错"不等于完成。
- 一个阶段要么按其批准的标准完整交付，要么不交付 —— 不拿演示冒充成品，不留下临时所有者、重复路径或拖欠的清理。
- 绝不用以下方式掩盖失败：移除核心功能、隐藏工作、无界等待或静默跳过步骤。

**并发**

- 只为真实依赖串行化（对同一共享资源的变更、由前一步产生的标识符）；仅仅共享一个资源池不构成依赖，提交顺序也不意味着处理顺序。
- 在最小的真实资源边界上持有并发所有权 —— 序号凭据、共享状态、任务、多步请求链是不同的东西。
- 停止时及时取消尚未广播的工作；已广播的工作要被追踪到确定的结局。

**性能**

- 延迟、可用性与吞吐量是功能本身，不是日后的润色。无界队列、sleep、大范围串行化和静默限流是缺陷的伪装，不是修复。
- 优化声明需要实测的前后对比，且本地延迟要与网络或外部服务的延迟分开计量。

**根因**

- 追溯：原始输入 → 生命周期 → 第一个非法转换 → 移除成因的最小变更。修复失败后，停止打补丁；回到原始输入，撤销无效的变更。
- 在相似的协议与共享路径上检查同样的成因 —— 但不把修改扩展到证据之外。

**架构与经济**

- 保持所有者边界（数据/RPC、协议、执行、策略、API、持久化、展示）；把稳定的共享能力抽象到狭窄的适配器之后，而不是为某个算法或某次事故抽象。
- 用产出的价值衡量文件、行数、状态与概念的预算 —— 一个局部 bug 不构成引入状态机的理由。
- 错误信息要点名相关对象、操作、上游响应与终止原因；"去看日志"不是给操作员的答案。

**测试**

- 测试用户的原始场景及其生命周期 —— 正常、失败、重启/恢复、终态对账 —— 而不只是编译通过或一条愉快路径。

## 领域扩展包示例：交易 / 链上交易

领域扩展包在主设计原则之上补充特定领域的条目，按需加载，其他项目无需为此付费。本包覆盖 CEX/DEX 交易与链上交易系统；要支持其他领域，照此方式衍生即可。阅读时在主设计原则之外叠加使用。

### 新的交易场所类型是扩展平台，而非替代

- 支持一种新的场所类型（如 DEX）是对既有交易平台的功能扩展 —— 不是孤立的演示。复用平台的认证、目录、参数/模板、任务生命周期、资产、历史、可观测性、告警与恢复能力。
- 按用户能力和生命周期映射不同场所，不做虚假的内部等价：swap 不是 IOC 订单；交易哈希不是成交；AMM 池不是订单簿；LP 不是挂单。
- 保持交互与视觉语言的一致，同时诚实地呈现场所特有的事实 —— 绝不为本无此语义的东西编造订单簿、订单或成交语义。
- 通过狭窄的适配器支持未来的链、场所与协议；协议专属的数学不进入公共执行路径。
- 为平台的核心业务流（swap、流动性提供、放量实验、跨市场跟价）保留可行的路径。

### 并发

- nonce 顺序不意味着接收顺序；核实用户批准的并发契约，而不是在预期可独立并行的地方强加过时的串行化。
- 在最小的真实资源边界上持有并发所有权 —— nonce、池状态、仓位、任务、交易链是不同的东西。

### 性能证据

- 延迟、可用性、可靠性与吞吐量是交易功能本身，不是润色。
- 交易优化的证明需要在授权下进行真实测试网的 A/B 实测；回放和直觉不足以确立改进。
- 在适用之处分别测量：本地计算、锁、排队、RPC/网络、场所接收、广播、上链、确认、状态投影 —— 并把本地延迟与外部 RPC、场所或链上延迟分开。

### 生命周期与运维

- prepared → broadcast → pending → confirmed/failed/unknown，加上停止、重启恢复与最终清理，必须在相关之处可观测。
- 错误信息要指明相关的钱包/账户、资产、操作、场所/协议响应与终止原因。
- 获授权的测试网实验要有问题、实测观察和结论 —— 不要因为会真实交易而回避，也不要漫无目的地跑。
